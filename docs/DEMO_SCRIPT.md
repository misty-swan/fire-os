# FireOS 営業デモ台本（宮之浦分団・5分）

営業担当の自分用の台紙で、そのまま案内を代行してくれる仲介者（分団の幹部の方など）に渡せる文書でもある。読み上げる文は「」、操作は番号どおり。所要は約5分。

## 0. はじめる前に（前提）

1. **URL**: `＜デモURL＞` — Task 7のデプロイで実URLが確定しだい、本書の`＜デモURL＞`をすべて置換する。お客様のスマホは事前にWi-Fiか4G/5Gへ。配置・公開手順の正本は `ops/demo-deploy.md` §5。
2. **体験アカウント3本**（氏名・役割は固定。**パスワードの値は本書にもGitにも書かない**。Git管理外の `.env.demo-login` か、営業資材の紙の台紙から渡す〔出典: ops/demo-deploy.md §2.1〕）:

   | メールアドレス | 役割 | 使う場面 |
   |---|---|---|
   | `demo-member@example.test` | 一般団員 | 手順①〜⑥（お客様に触っていただく本体） |
   | `demo-officer@example.test` | 幹部 | 手順⑤の承認だけ |
   | `demo-admin@example.test` | 管理者 | 「二要素」の説明（§2）だけ |

   週次リセット後も同じパスワードがSecretから自動で再設定されるため、台紙の書き替えは不要〔出典: ops/demo-deploy.md §3.1〕。
3. **データは全て架空**。面会の最初に、画面上部に常に出ている **「架空データによる検証版です」のバッジ**を指して必ず一言添える: 「地図も団員も記録も、すべて架空の検証用データです。実データは入っていません」〔出典: src/client/components/AppShell.tsx・ops/demo-deploy.md §1〕。団体名だけは実在の地名を使った「宮之浦分団」で、人名・施設・写真・文書はすべて架空である旨を同じ呼吸で伝える。
4. **週1回（月曜01:00 JST）にデータは初期化**される。お客様が入れた記録も消えるため、先に「お試しの入力は残りません。毎週月曜朝に初期化しています」と伝えておく〔出典: ops/demo-deploy.md §3.1〕。

## 1. 5分の動線（時間は目安）

### ① ログイン（0:00〜。一般団員で入る）

1. `＜デモURL＞/login` を開き、`demo-member@example.test` とパスワードでログインする（デモ用アカウントは二要素なし・パスワードだけ）。
2. 一言: 「本番は分団の管理者からの招待リンクと二要素認証で始めます。今日は触っていただくための特別なデモ用アカウントです」〔出典: docs/USER_GUIDE.md §1・ops/demo-deploy.md §2.1〕

   見せどころ: ログインにアプリの登録や手続きが要らず、招待があれば当日から使い始められる。

### ② ホーム（0:30〜。今日やることが数字で分かる）

1. 上部の「これからの予定」のダイヤルと、「本人未回答」「確認待ちの異常」「点検期限」「自分のタスク」の数字を見る。
2. 数字のタイルを1つ押して、同じ件数の一覧がそのまま開くことを見せる（全部は回さない）〔出典: docs/USER_GUIDE.md §2〕。

   見せどころ: 「出勤後に何をすべきかが数字で一目。押せばその一覧なので、数字と実態がずれない」。

### ③ マップ（1:00〜。宮之浦の地理と施設マーカー）

1. 下のタブ（PCは左サイドバー）で「マップ」を開く。宮之浦周辺の地図に、消火栓・防火水槽・資器材箱のマーカーが立つ。
2. 種別チップで「防火水槽だけ」に絞り、件数が変わることを見せる。管理番号（`MY-0001` など）での検索も1回。
3. マーカーを押すと選択シート（PCは右の一覧・詳細）が出る。「一覧」切替も1画面だけ見せる〔出典: docs/USER_GUIDE.md §3〕。

   見せどころ: 「水利の位置が団員全員のポケットに入る。新団員でも場所を聞かずに現場へ行ける」。

   注: 地図はGoogle Mapsの実タイル（キーがある環境。キーが無い環境では置き換え絵に自動で切り替わる）〔出典: docs/16 T089・docs/superpowers/plans/2026-10-21-public-demo-miyanoura.md Task 2〕。シートのボタンからGoogleマップの経路案内にも飛べる。

### ④ 点検登録（2:00〜。お客様に触っていただく）

1. マーカーの選択シートの「点検する」→ 点検様式を選び、項目を「良好」にして進む。
2. 「写真・メモへ進む」で写真1枚とメモ1行、「確認へ進む」→「点検を保存」〔出典: docs/USER_GUIDE.md §3〕。

   見せどころ: 「紙の点検票と同じ感覚のまま、写真つきで記録が終わる。途中で圏外になっても入力は端末に残る（§4のQA3）」。

### ⑤ 「異常あり」にしたときの流れ（3:00〜。起票→点検管理→AI分類の提案）

1. もう1件、同じ点検を今度は「異常あり」で保存する。保存前の確認画面に**異常の報告が作られる旨が出る**こと、保存後に**報告（起票）が自動で作られる**こと（施設の状態が「異常報告あり」になる）を見せる。
2. 「点検管理」（スマホはメニュー）で、作られた報告と状態（確認待ち→…）を開く〔出典: docs/USER_GUIDE.md §3〕。
3. 「AIレビュー」（メニュー）で「AI分類を依頼」→ AIが分類と対応候補を**提案**する〔出典: docs/USER_GUIDE.md §5〕。承認まで見せるなら幹部アカウント（`demo-officer@example.test`）で入り直して「修正して承認」（依頼と提案の確認は自分の点検なら団員のままでもできる。承認は幹部以上〔出典: docs/10_権限マトリクス.md PER-09/10〕）。

   見せどころ: 「AIは分類を提案するだけ。原文と差分を見て、確定するのは必ず人」。

   注: AIの応答は数秒で戻る。うまくいかないときは深追いせず、「提案までAI、確定は人」という言葉に戻って先へ進む。

### ⑥ 出欠回答（4:00〜）

1. 「予定・活動」で直近の予定（デモでは架空の防災訓練）を開き、「参加」で回答する〔出典: docs/USER_GUIDE.md §2・scripts/seed-demo.ts〕。

   見せどころ: 「回答が管理者側へ自動で集計される。紙の出席簿と回収の電話がなくなる」。

### ⑦ 締め（4:30〜）

1. 言葉: 「いま見ていただいたのは、日頃の点検・連絡・記録のための道具です。**実災害時の正式な指令・連絡は、いままでどおり既存の系統（無線・電話・連絡網）が正**。FireOSは記録と補助のためのものです」〔出典: docs/14_設計判断・未決事項.md D08・docs/USER_GUIDE.md 冒頭の原則〕
2. 正式導入までの流れ（資料とチェックリストのご確認→回答の記録→実環境での残手順→正式リリース判定→実データ投入）は、提案資料 `docs/ADOPTION_PROPOSAL.md` §6 に沿って一言で添える。
3. 締めの一言（例）: 「まずは点検と出欠だけでも、1分団で試せる形です。使いながら『これは要らない』も教えてください。それを踏まえて正式導入のご判断材料にします」。

## 2. 「二要素が要る機微操作」を見せる（セキュリティの証として）

1. やり方: 管理者アカウント（`demo-admin@example.test`）でログインし直し、「管理」画面（団員の管理・監査ログ・運用〔費用と障害〕）を開く。**「二要素認証の設定が必要です」の案内が出て、操作ができない**ことを見せる〔出典: src/client/features/admin/AccessPanel.tsx・docs/10_権限マトリクス.md PER-06/07/08〕。
2. 台詞（例）: 「団員の個人情報・権限・監査・費用といった機微な操作は、パスワードに加えて認証アプリの6桁コード（二要素認証）が済んだ管理者しかできません。このデモ用アカウントはご覧いただくためにわざと二要素を外してあるので、こうして拒否されます。導入時には必須です」。
3. 注意: 体験管理者で管理操作はできない（仕様）。管理操作そのものを実演したいときは、営業担当が自分用に二要素設定した管理者アカウントを使う〔出典: ops/demo-deploy.md §2.1〕。見せたら元の団員アカウントへ戻す。

## 3. QRコード（URL確定後に作る）

1. **いまは作らない。** Task 7のデプロイで実URLが確定してから作る（URLが変わると作り直し）。案内先は `＜デモURL＞/login`（ログイン直行。ランディングを挟まない）。
2. 手早く作る（端末で）: `qrencode -t UTF8i '＜デモURL＞/login'` — 端末にQRが文字でその場表示される（黒背景の端末向けの反転表示。読み取りに難があるときは `-t UTF8` へ。インストール例: `sudo apt install qrencode`）。表示をコピーして台紙に貼る。
3. 無料のWeb生成サービスを使う場合: そのサービスの利用規約（商用利用の可否・生成したコードの扱い・広告表示の有無）の**直近の版を必ず確認してから**使う。営業印刷物への掲載が許可されているかを、担当ごとに必ず確認する。
4. 印刷物への配置例: チラシの右下に1辺2cm以上で配置。QRの下に「ログイン: ＜デモURL＞ ／ メール: demo-member@example.test」と文字でも併記（読めない端末向け）。**「データはすべて架空です（検証版）」の一文をQRの近くに必ず入れる。** 印刷後に実機2台（iPhone・Android）で読み取りからログインまでを確認する。

## 4. 想定QA（8問）

1. **費用はどのくらい？** — Workers Paidの$5/月を基本とすれば、代表使用量の範囲では追加費はほぼ0（AI・D1・R2が枠内の間）。ただし$0運用は保証しない。地図は月2,000ロードの枠をGoogle Cloud Console側の割当で確保する〔出典: docs/evidence/cost-estimate.md・ops/demo-deploy.md §4.3〕。
2. **データはどこから？実データは入っていない？** — すべて自動生成の架空データです。実名簿・実水利・実写真は入らない。実データの投入は、正式導入の了承と設定の記録の後です〔出典: ops/demo-deploy.md §1・docs/ADOPTION_PROPOSAL.md §6〕。
3. **圏外だとどうなる？** — 入力は端末に下書き保存され、通信が戻ると自動で同期されます。保存の結果が確認できないときは「保存しました」と言わず、正直な表示が出ます。状況は「同期の状況」で確認できます。通信断のときも正式な連絡は既存の系統です〔出典: docs/USER_GUIDE.md §7・§8〕。
4. **セキュリティは？** — 本番とデモは実行環境・データベース・保存領域・鍵をすべて別にして分離しています。誰が・いつ・何をしたかは監査に残ります。管理者の機微操作は二要素認証が必須。通知の送信も人の承認が要ります〔出典: ops/demo-deploy.md §1・docs/07_セキュリティ・運用設計.md・docs/10_権限マトリクス.md・docs/USER_GUIDE.md §4〕。
5. **スマホ以外でも使える？** — ブラウザが動くスマホ・タブレット・PCで使えます（画面は幅で最適化します）。実端末での最終確認は、正式導入前の残手順として進めています〔出典: docs/USER_GUIDE.md 冒頭・docs/evidence/release-decision.md〕。
6. **導入までの流れは？現在はどの段階？** — 提案資料§6のとおりです（資料・チェックリストのご確認→回答の記録→実環境での残手順→正式リリース判定→実データ投入）。現在は開発版の完成と公開デモの段階で、**正式リリース判定は未了**（現時点の判定記録は「不可」。団体側の20項目の回答待ちです）〔出典: docs/ADOPTION_PROPOSAL.md §6・docs/evidence/release-decision.md §1〕。
7. **今日入れたデータは残りますか？** — 残りません。毎週月曜01:00 JSTにデモは初期化されます（週次リセット。体験アカウントのパスワードは変わりません）〔出典: ops/demo-deploy.md §3.1〕。
8. **通知はどこまで届く？** — 現在はアプリ内の通知です（Web Push・メール等の実チャネルは未実装）。届いたか分からないものは「到達不明」と正直に表示し、既存の連絡手段での確認を促します〔出典: docs/14_設計判断・未決事項.md D13・docs/USER_GUIDE.md §4〕。
