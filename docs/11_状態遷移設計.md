# 11 状態遷移設計

版：v0.3 / 2026-10-13 / B案・未承認。状態コードとDB/API/UIの意味の正本。業務承認者・締切・点検基準は14で決定する。

## 1. 共通契約

状態は自由文字列でなく列挙/CHECKで制約する。変更要求は`version`・必要理由・前提状態を含み、サーバーが遷移とPERを検査する。未知状態は400、許可外遷移は422、旧版は409、認可失敗は403/404。成功時だけ状態履歴と監査を同一D1単位で追記する。訂正理由を残すが、個人情報本文を監査へ複製しない。

## 2. 状態と許可遷移

| 概念 / 初期値 | 許可遷移・操作 | 権限・前提 | 履歴・副作用 |
|---|---|---|---|
| 位置確認 `unverified` | unverified→pending（確認依頼）、pending→verified/rejected、verified/rejected→unverified（座標/出典変更） | PER-03、確認対象locationVersion一致、確認者D09 | facility_location_revisions。座標変更は必ず新locationVersion、旧確認を残す |
| 点検結果 `unknown` | 保存原本の値はok/needs_review/unknown。保存後の値変更は新訂正版 | PER-04、承認様式/必須項目D06 | 原本不変、revision/明細保存。結果から設備使用可否を自動更新しない |
| 異常 `reported`（確認待ち） | reported→under_review、under_review→in_progress/closed、in_progress→resolved、resolved→closed/in_progress、closed→under_review（再開理由） | PER-05、D07の担当/確認責任、閉鎖/再開理由必須 | issue_events＋監査。resolved＝対応実施、closed＝確認終了/非該当。確認済位置とは無関係 |
| 開催 `draft` | draft→scheduled/cancelled、scheduled→in_progress/cancelled、in_progress→completed、completed→in_progress（訂正再開） | PER-03/04、日時整合、公開対象、理由。D05 | activity_events。中止で既存出欠を削除しない。実績とは別状態 |
| 出欠 `unanswered` | unanswered/attending/absent/undecided間の変更、受付中のみ | PER-02本人、代理条件/締切D05、version一致 | attendance_events。未回答は回答レコード未作成でも表現し、未定と区別 |
| 実参加 `unconfirmed` | unconfirmed→participated/absent、訂正はparticipated↔absent/unconfirmed | PER-04、実績版/訂正理由D05 | activity_result_revisions/参加版。出欠回答を実参加へコピーしない |
| 出動イベント `recording` | recording→active/closed/voided、active→closed、closed→recording（訂正）、voidedは閲覧のみ | PER-04、D08、訂正/無効化理由 | incident_events。simulation/training/actual_recordの種別と状態を分離。正式指令を発行しない |
| 参集/帰還 `unconfirmed` | unconfirmed→unavailable/mobilizing/arrived/returned、mobilizing→arrived/unavailable、arrived→returned、履歴訂正は別イベント | 本人/代理PER-04、D08、時刻順とversion | incident_participant_events。returnedは帰還記録、absentとは別。事後入力では欠落時刻を捏造しない |
| 永続ジョブ（AI処理を含む汎用。API-86） `queued` | queued→running→succeeded/retry_wait/manual_review/**stale**、retry_wait→running、running期限切れ→retry_wait、未実行(queued/retry_wait)→cancelled。**stale**=実行中に元版が変わり/権限を失い結果を採用できない（T006で追加、終端）。作業権の期限切れ時に試行上限へ達していれば manual_review | 内部job handler、lease token一致、最大試行数02 | jobs。業務原本は消さない。成功候補も人未承認 |
| AI提案 `pending` | pending→approved/approved_with_edit/rejected、元版/権限更新→stale | PER-10、元版/提案版一致、業務反映先権限 | review_decisions一回、effect操作ID。staleは再生成/再レビュー、旧決定書換なし |
| 業務タスク `open` | open→assigned/in_progress/cancelled、assigned→in_progress/cancelled、in_progress→done、done→in_progress（再開理由） | PER-04/10、担当/対象権限、AI起点は承認effectから作成 | tasks＋task_events、訂正/再開の履歴。提案pendingはai_evaluationsで管理 |
| 報告書/文書版 `draft` | draft→in_review、in_review→approved/changes_requested、changes_requestedの訂正は新draft版、approved→superseded/withdrawn | PER-10/11、D20、引用元/実績版一致 | report_versions/document_versions。申請はcontent_version_eventsのみ、審査の最終決定は一版一回。差戻し後/承認後訂正は新draft版、旧版不変。承認済pointerは次版承認まで保持 |
| 添付 `pending_upload` | pending_upload→uploaded→checking→ready/rejected、期限切れ→expired、ready→deleting→deleted | 申請者/対象PER-04、実体検査。削除D10 | attachment_events。ready前取得不可。リンク中は削除拒否か承認unlinkを要求 |
| お知らせ `draft` | draft→published/archived、published→archived、編集で新revision | PER-03、対象者と公開日時D03 | announcement_revisions。対象変更は新通知承認。既読は版に束縛 |
| 通知承認 `draft` | draft→approved/cancelled、approved→dispatching→finished/failed。「未送分取消」は配送単位(deliveries)の取消で、承認全体の状態は変えない（承認全体を止める場合は配送前のapproved→cancelledをT050で追加検討） | PER-12、本文/対象者版承認、配送D13 | notification_events/ deliveries。送信済みを未送へ戻さない |
| 配送 `pending` | pending→sending→provider_accepted/failed/unknown、failed/unknown→retry_wait→sending | 内部処理、配信キー固定、再試行上限 | provider_acceptedは端末到達保証でない。既読はnotification_recipients.read_at/本人API-100 |
| 同期操作 `local_draft` | local_draft→pending→sending→applied/conflict/rejected、conflict→編集した新操作、sending応答不明→照会 | PER-13/対象の元権限、再認証、baseVersion | IndexedDB下書きとsync_operationsを分離。applied前に保存完了を表示しない |
| 巡回計画 `draft` | draft→confirmed/cancelled、confirmedの変更は新revision | PER-14、D01採用時、人が対象/順番確認 | patrol_plans。AI案から自動指示しない |

実参加/参集のコードへの日本語対応は上表で固定し、UIは「参加予定」「実参加」「参集済」「帰還記録」を別表示する。設備の正式な使用可否は本システムで自動算定しない。必要な公式項目の導入はD06/D08で管理主体が決定する。

**暫定扱い（PH1以降で確定）：** 名簿は`active/paused/retired`（04）のみ列挙化。車両・資機材・様式・文書全体・取込み・出動以外の`status`はAPI契約では自由文字列(`provisional`)で、各機能タスクで列挙とCHECKを追加する。ジョブ状態の遷移辺は`src/shared/states.ts`が正本（T002）。

## 3. 訂正・取消

原本点検・実績版・承認記録・監査はUPDATEで書換えない。新訂正レコードに`supersedes_id/reason/actor/at`を持ち、現在版pointerの切替もversionガードする。既に解決した異常の訂正で自動再開/削除しない。担当者に再確認タスクを作る案としD07で確定する。取消も過去の参加/配送/使用履歴を消さず、集計は無効なoperationを除く。

## 4. 状態に依存する試験

正常な各辺、未許可の逆辺、旧version、別担当、二重承認、元版変更、途中SQL失敗をCT-01〜06/ATの該当要件で検証する。送信/処理状態と現実の事実（実到着・安全・設備使用可否）を同一視しないUIをAT-MAP-07/AT-COM-02/AT-DSP-02で確認する。
