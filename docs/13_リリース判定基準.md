# 13 正式リリース判定基準

版：v0.3 / 2026-10-13 / 未承認。正式リリース条件の唯一の正本。設計改訂完了・PoC・架空データプレビュー・限定試験を正式リリースと呼ばない。

## 1. 対象台帳

12の原文54件を全件保持。機能41件＋非機能10件＝51件は初回必須、MAP-10/AI-06/AI-07の3件はD01採用確認待ちで除外しない。D01を決めるまでは判定に使う対象版を特定できず正式判定不可。採用決定した3件も初回必須であり、未実装/品質未達を後版延期で免除しない。開発者による対象削減は禁止。IDなし参考候補は採用決定なしに必須へ昇格しない。

## 3. 判定手順

1. D01採用範囲を決定し、判定時点の対象ID/文書版/Git commitと承認者を記録。docs自体は凍結せず更新可能とし、以後の変更で影響する試験・ゲートは再判定する。
2. 12の全行を実装/設計/テスト証跡へ結び、未定義/未実装/未実施/skipを列挙。担当者自己申告だけで完了にしない。
3. 全ゲートの合格根拠とD/V完了を独立reviewし、管理主体の許諾/運用/費用/契約判断を確認。
4. 開発責任者と管理主体がリリース版/日/対象/環境/復旧点/runbookを承認。全ANDが揃わなければ「正式リリース不可」。
5. リリース後の障害は07に従う。障害時縮退設計があることは未実装でのリリース許可ではない。

## 4. 文書の完成と製品の完成

v0.3文書の改訂完了は、要件保全、仕様間整合、明確な修正反映、未決/検証の可視化ができた状態。業務未承認・技術未実証のdraftを承認済み設計や稼働可能な製品と表現しない。現在の全RGは未達であり、本改訂をもって正式リリースを許可しない。

## 5. 完成後に消防団へ提案する順序

設計書を完成→架空データで全採用機能を実装・統合・試験→完成したアプリを消防団へ提案→実際の運用/情報利用/費用の了承と設定を確認→実データ投入・正式運用開始。組織の了承を、設計書や架空データのアプリを作り始める条件にはしない。実運用の了承を得たことにせず、正式リリースの全ゲートも省略しない。
