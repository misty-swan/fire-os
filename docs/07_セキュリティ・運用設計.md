# 07 セキュリティ・運用設計

版：v0.3 / 2026-10-13 / 未承認。PH0で冪等・監査の追記専用化・試験用認証の環境限定を実装、認証/添付/通知/端末保存/復旧は未実装。認証ライフサイクル、添付、端末保存、通知、復旧/料金運用の正本。業務権限10、状態11、決定14、判定13。

## 1. 運用境界・データ分類

正式指令/119/現場指揮/安否確認の唯一の手段としない。実災害の許容用途と既存系統の代替手順はD08、管理主体/窓口/代行はD17。実データ利用許諾・個人情報・消防水利台帳・帳票規程の承認を要する。公開デモは架空人物/地点/写真のみ、本番/staging/demoを別Worker/D1/R2/Google key/AI設定へ分離する。

分類はBASIC/PERSONAL/SENSITIVE/SECURITY（10）。名簿/連絡先/出欠、非公開水利、現場写真、AI本文の必要最小化と項目ACLを全経路へ適用。SecretはCloudflare Secrets、ブラウザMapsキーは露出前提のリファラー/API制限で保護。ログにtoken/パスワード/正確な非公開位置/AI全文を無条件保存しない。

## 2. 認証・招待・権限のライフサイクル

Better Auth採用はB案（D04/V01）。固定版は1.7.7（2026-10-14、局所のworkerdで確認。実Workersは未確認）。公式にD1 binding/Drizzle SQLite adapter/Hono handlerの手段がある。ライブラリが業務名簿/担当/許諾を代行するわけではない。[Better Auth D1](https://better-auth.com/blog/1-5)、[Hono](https://better-auth.com/docs/integrations/hono)

| 段階 | 操作/保存/不正時の処理 |
|---|---|
| 初期管理者 | 運用担当の管理CLI相当の一回手順を将来実装。環境とunit/本人を照合、bootstrap完了を監査し無効化。公開初期登録エンドポイントを残さない |
| 招待発行 | PER-07、未リンク名簿を指定、暗号学的乱数tokenを一回表示/承認配送、DBはhash。期限48h案、対象email/認証IDに束縛、重複有効招待は取消して再発行 |
| 招待利用 | 所有確認済認証identityと名簿を照合。期限/取消/未使用/member未リンクを同batchで検査しconsume＋link。別団員選択やroleの自己申告は拒否 |
| 認証 | auth handlerでcredential検査、業務APIで最新users/members/所属を再検査。未招待のライブラリsign-up/OAuth自己登録経路も拒否 |
| 再設定/MFA | 期限・一回性・所有確認、レート制限、成功後旧session失効。回復コードはhash、表示一回。方法/配送/MFA範囲はD04承認 |
| 権限変更 | PER-07、対象役割/範囲、自己昇格/最終管理者保護、authz_version増分＋監査。同時業務更新が古い権限を使わないよう02でassert |
| 退団/停止 | users/membersを停止、authz_version増分を先にcommitして新業務要求を遮断。全session revokeを実行し失敗は永続jobで再試行。認証側停止との間も業務middlewareが拒否 |
| 管理者復旧 | 管理主体が本人確認/二者確認する案。通常のパスワード再設定を優先、失敗時限定break-glass手順/期限付き権限/監査/回復後全session失効。本人判断だけの自己昇格は禁止 |

認証固有DB書込と業務招待消費を同一transactionへ接続できるかV01で検証。不可なら認証アカウントの事前作成を許しても、招待消費/名簿リンク未完了のidentityには業務アクセスを一切与えない。孤児アカウントの回収を定義する。名簿停止とsession revokeを外部的に原子的だと偽装しない。

同一origin、Secure/HttpOnly/SameSite Cookie、固定trustedOrigins/baseURL、CSRF/Origin検査（自作業務APIにも）、CSP/エスケープ、型/サイズ検証。認証/回復/AI/アップロード/検索のレート上限案はIP＋user単位で計測固定（D18）。生ログやdebugにcredentialを出さない。Cookie session cacheは業務認可に使わず、失効後のキャッシュ残存を避ける。[Better Auth Sessions](https://better-auth.com/docs/concepts/session-management)

## 3. 添付ライフサイクル

**取得はWorkers認可＋R2 binding streamを選ぶB案。署名GETへredirectしない。** 署名URLはbearerで期限内利用が残るため、退団/権限変更後の新規取得要求を拒否する契約に合わない。既に取得済みのファイル回収・開始済streamの瞬時停止は保証しない。[R2署名URL](https://developers.cloudflare.com/r2/api/s3/presigned-urls/)

1. API-26で対象ACL/分類/容量/形式を検査してintent（15分案）を作る。名前/パスはサーバー生成、元ファイル名は表示用に無害化。対象が未作成ならAPI-98でowner/unit/予定entityType/既存親を持つattachment_draftを予約し、intentを束縛する。最終業務mutationで作成先/分類/親を再検査し予約を一回consumeする。
2. API-83で認可/有効intentを検査し、試行専用の不変staging keyへstream転送。受信サイズを実測、上限超過中断、hashを計算。再送はattempt/hashを照合しready実体を上書きしない。
3. API-84はuploadAttemptId/hash/実体HEADを検査しchecking jobをD1保存、202。検査workerはmagic bytes/実体decoder/サイズ/ページ数等を検査。JPEG/PNG/WebP/PDF/UTF-8 CSVを許可する案（業務必要形式はD20、上限20 MiB/写真10 MiB案）。CSVは列/行/encoding/式注入を検査しimport専用で処理、HTMLとして配信しない。SVG/HTML/実行ファイル・偽装拡張子は拒否する案。
4. 写真は安全な再エンコード/EXIF除去、PDFはmalware検査/危険埋込の検査方針をV02で実証。検査環境がWorkersだけで成立しない場合はCloudflare中心を維持した外部検査/変換の契約・費用・データ送信をD16/D12で判断し、検査を無言省略しない。
5. 合格した不変ready key/hashをD1へcommit。stagingを公開せず、確認済実体を別キーに固定して遅延uploadで書換えられないようにする。完成・業務mutation時に添付状態/同unit/対象権限/分類を再検査しlinkする。
6. API-27は現session/停止/対象ACL/readyを確認しstream。機微内容はCache-Control private,no-store、共有CDN/Service Workerへ保存しない。Content-Type/nosniff、Content-Disposition attachmentを危険形式/PDFに使用する案。画像表示も検査済実体のみ。
7. API-101 unlink/削除は理由・版・監査、リンクが残る削除は422。削除予定tombstone→保持期間→R2削除→照合を行う。intent期限切れ/孤児は定期照合し、復元に必要なキーは回収しない（D10）。

容量/形式だけで安全を保証しない。外部公開スキャンサービスへ実写真を無断送信しない。[OWASP File Upload](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)

## 4. PWA・GPS・オフライン同期

PWAは正式採用技術。Service Workerはアプリshellの版付きassetだけをprecache、Googleのscript/tile/image、認証レスポンス、添付本文、RAG回答/名簿の機微レスポンスは自動cacheしない。自前下書きはIndexedDBにuser/unit/device別で保持する案、暗号化を使っても端末ログイン済みの保護を過大評価しない。

同期対象案は点検/写真下書き、本人出欠、出動参集の入力保留（DSP-05を含む）。具体的な端末保存範囲/上限/期限/共有端末条件はD14。保持7日案、ログアウト/ユーザー切替でデータと鍵を破棄。オフラインの遠隔失効/回収は保証不能なので、TTL・再認証・端末ロックを併用しD14で承認する。

各操作はclientOperationId、baseVersion、payloadHash、必要添付intent参照を持つ。再接続→session再認証→元対象ACL再検査→添付転送/検査→同じ元業務APIを呼ぶ。適用済operationの再送は同結果。旧versionはconflict、人が現在値と下書きを比較し新操作を作る。Last-write-winsや旧参集状態の自動上書きをしない。応答不明はoperation照会し、pending/appliedをUIで区別する。

GPSは一回取得/accuracy/時刻表示、失敗/低精度は手動確認。現在地を業務表へ常時記録しない。位置を保存するのは施設登録/訂正で明示確定した座標のみ、端末位置のログ保持はD09で最小化。PWA更新は未同期データを消さず、互換不能payloadは移行/再入力を明示する。

リアルタイムは認可済D1イベントの通知。接続時/イベント/再接続で現ACL、sequence欠落はAPI snapshotで復旧。停止/権限変更時に接続を閉じ、切断検知が遅れても新規データを配信しない。方式・更新遅延目標はD16/D18。DO採否を未実装許可と混同しない。

## 5. 通知・既読・代替連絡

通知チャネルはD13。推奨はアプリ内通知＋Web Pushまたはemailの一経路、既存正式連絡と併用。対象/本文の版/hashをAPI-64で明示承認、承認時現在の宛先/対象権限も検査。再配送はrecipient＋通知版のdeliveryKeyを固定。providerが冪等未対応なら送信結果不明時に照会/手動確認し、無限再送しない。

queued/sending/provider_accepted/failed/unknown、本人readは別。端末到達・既読・参加意思・安否の保証をしない。送信済の取消はできず未送分だけ止める。期限切れ/退団済対象を配信直前に除外し理由を記録。点検期限/未回答の自動検出は決定論、通知送信は業務で承認したルール/本文/対象の範囲に限定。自動送信許可の規程自体はD13未承認。

アプリ障害・通知遅延時の正式連絡は既存の責任系統で実施。電話/無線/既存連絡網などの具体手段/責任者は管理主体D08/D17が決める。FireOSだけで災害時連絡を完結したと表示しない。

## 6. Google Mapsと公開条件

browser keyはMaps JavaScript APIと許可originに限定、環境別key、請求/利用量監視。予算アラートは課金停止でない。初回はDynamic Maps中心で、別SKU（Places/Geocoding/Routes/Street View）を意図せず呼ばない。MAP-09はMaps URLリンクを用いAPI呼出しを追加しない。

利用規約/Privacyはpublicにアクセス可能、Google規約/Privacy参照、Google帰属を隠さない。独自台帳/GPS/Google由来データは出典で分離し保存条件を確認。[Maps JS Policies](https://developers.google.com/maps/documentation/javascript/policies)、[Google Security Guidance](https://developers.google.com/maps/api-security-best-practices)

High Risk Activities条項を用途別に確認する。平常管理/訓練でも名称だけで適合を断定せず、実災害の生命安全依存用途はD08で契約判断。確認不能なら平常管理と現場用途の分離、現場向け別地図基盤を比較し、Google採用方針/必要機能を無断変更しない。[Google Maps Terms](https://cloud.google.com/maps-platform/terms)

## 7. バックアップ・復旧・管理者代行

D1 Time TravelはFree7日/Paid30日で、R2本体の復元ではない。[D1 Limits](https://developers.cloudflare.com/d1/platform/limits/)

提案：D1を日次exportしアクセス限定の別保管先へ、R2は不変キー/削除猶予/manifestと重要原本の別複製を用意。保存/複製/削除猶予の具体年限はD10、RTO/RPOは推奨24時間/24時間案と実測から承認。アプリ利用頻度だけで損失許容を確定しない。

復旧runbook：影響把握→新規mutation/配送停止→原因/復元点/manifest選定→stagingでD1復元→必要R2キー存在/hash照合→欠落/孤児/重複/集計/ACL照合→sessions失効/authz_version更新→旧job/effect/配送状態照合（外部送信を再実行しない）→限定確認→管理主体承認→再開→証跡保存。R2を先に削除してDBだけ戻す手順は禁止。migration復旧とアカウント喪失の演習も行う。

代行管理者の本人確認/連絡/Secret回復、最後の管理者保護、費用/障害アラートの副担当をD17で決める。漏えい/端末紛失時は対象停止・session失効・ログ保全・関係者連絡・影響照合の窓口を定める。実データ投入前に復元演習、正式リリース前に全機能込み再演習する。
