# 07 セキュリティ・運用設計（ドラフト）

## 1. 前提・運用境界

FireOSは消防団の事務・情報管理を支援する。**正式な出動指令・119番通報・現場指揮・安否確認の唯一の手段としない**。実データを投入した運用は、対象団体・自治体等との合意、規程、利用許諾を確認したうえで実施する。

## 2. データ分類

| 区分 | 例 | 方針 |
|---|---|---|
| 公開デモ | 架空の団員・施設・活動 | デモ環境に限定。公開可能 |
| 個人情報 | 団員名、連絡先、出欠・参加記録 | 最小限収集、権限に応じて非表示 |
| 内部業務情報 | 点検記録、施設台帳、修繕対応 | ログイン・権限管理下で閲覧 |
| 機微な業務情報 | 非公開施設位置、実出動、現場写真等 | 限定アクセス、外部共有に別途承認 |
| 秘密情報 | セッショントークン、APIキー | Cloudflare Secrets等で管理し、画面・ログに出さない |

## 3. 認証・認可

- 招待制アカウントを基本とする。退団・休団時の無効化を明示的に実装する。
- 「一般団員」「担当者」「幹部」「システム管理者」を初期ロール候補とする。
- サーバー側の **RBAC（役割による認可）＋リソース/分団単位の条件検証** を必須とする。
- 認証ライブラリはBetter Authを候補とする。実装前にWorkers/D1との互換性・パスワード再設定・セッション失効・CSRF防御を確認する。
- 権限変更・重要データの承認・添付取得のログを適切に残す。
- 管理者向け多要素認証は導入段階と運用負荷を検討する。

### 操作権限の例

| 操作 | 団員 | 担当者 | 幹部 | 管理者 |
|---|---|---|---|---|
| 地図・予定閲覧 | ○ | ○ | ○ | ○ |
| 自分の出欠登録 | ○ | ○ | ○ | ○ |
| 点検・異常の報告 | ○ | ○ | ○ | ○ |
| 施設マスタ変更 | × | △担当範囲 | ○ | ○ |
| AI候補の確定承認 | × | △担当範囲 | ○ | ○ |
| 利用者招待・権限変更 | × | × | △合意範囲 | ○ |

`△`は業務規程確定後に実装する条件付き権限である。

## 4. Google Mapsに関する管理

- Google CloudのAPIキーは **Maps JavaScript APIに限定**し、WebアプリのHTTPリファラー制限を行う。
- フロントに渡すブラウザ用APIキーと、その他のサーバー秘密情報を混在させない。
- Google Cloudの請求先・予算アラート・使用量確認の運用担当者を決める。
- **予算アラートは自動的な課金停止ではない**。異常利用時にキー制限・クォータ等で対処する手順を設ける。
- 初期はPlaces/Geocoding/Routes/Street Viewなど別料金となり得る機能を原則追加しない。
- Googleマップのタイル・画像を独自に取得・保存・オフライン配信する設計は採用しない。
- 地図が利用できない場合でも、許可された利用者は施設一覧・座標・点検履歴を参照できるようにする。

料金・APIの条件は [Google公式料金ページ](https://developers.google.com/maps/billing-and-pricing/pricing) で導入前に再確認する。

## 5. R2ファイルの保護

- 添付ファイルはデフォルト非公開のバケットに保存する。
- 認可済みのAPIでのみ短寿命のアクセス手段を発行し、対象レコードへのアクセス権を検証する。
- MIMEタイプの申告値だけを信用せず、容量・実体・拡張子の整合性を確認する。
- アップロード時のメタデータ・所有者・対象IDを監査可能とする。
- 退団や役割変更後には権限外ユーザーが旧URL経由で取得できないか検証する。
- 写真の位置メタデータ（EXIF）について取り扱い方針を定め、不要なら削除する。

## 6. データバックアップと復元

| 対象 | 方針（案） |
|---|---|
| D1 | 本番導入前にバックアップ・エクスポート・復元の手順と実施者を決める |
| R2 | 重要添付の保持・削除、誤削除対策、バックアップ要否を評価する |
| 設定・秘密情報 | リポジトリに直接記載せず、権限を限定する |
| スキーマ変更 | マイグレーションをバージョン管理し、戻し方を記録する |
| 復元テスト | ステージング環境で手順とデータ整合性を検証する |

復旧時間（RTO）・許容データ損失（RPO）は**未決定**。正式導入前に運用主体の許容範囲を合意する。

## 7. ログ・監視

- 監査対象：招待・ログイン失敗傾向・ロール変更・施設台帳の更新・点検承認・異常解決・AI提案の承認。
- 障害監視：Workersエラー率、p95応答、DBエラー、R2アクセス失敗、AI実行失敗、Google Mapsロード失敗。
- 料金監視：Workers/D1/R2/AIの使用量とGoogle Mapsの課金・クォータを月次確認する。
- セキュリティ：トークンや本文の機微情報をログに含めず、必要に応じて識別情報をマスクする。
- 保存期間、ログ閲覧権限、アラートの通知方法を正式運用前に決める。

## 8. 障害時の動作

| 事象 | 暫定対応方針 |
|---|---|
| Google Maps表示不可 | 施設一覧・詳細を利用。地図なしで施設の文字情報を参照 |
| Workers/D1停止 | 既存の消防団連絡・指揮系統を使用し、復旧後に記録を補完 |
| Jev/LLM停止 | 手動で報告・分類・記録を行う |
| モバイル通信断 | 初期版では保存成功を装わない。P1でオフライン下書きを検討 |
| クラウド課金異常 | キー制限・APIクォータ・利用停止手順に従い影響を抑制 |
| 誤登録・誤更新 | 監査ログと変更履歴で原因を追跡し、権限者が訂正 |

## 9. 公開デモと実運用の分離

- リポジトリは架空データと安全なデフォルト設定のみを含める。
- 本番とデモでCloudflare環境、D1データベース、R2バケット、Google Cloud認証情報、AI利用設定を分離する。
- ポートフォリオ画面のスクリーンショットに実施設・実団員・出動の非公開情報を含めない。
- 実団体のデータ利用は、消防団だけでなく自治体や情報保有者の管理ルールも確認する。

## 10. 運用開始前に必ず決める事項

1. 利用目的、管理主体、承認者、問い合わせ先。
2. 個人情報や非公開施設情報の利用可否・保管期間・アクセス範囲。
3. AIに送れるデータの分類、外部提供・国外処理の判断、ログ保持。
4. 正式連絡とFireOSの役割分担、障害時の代替手順。
5. 本番・デモのデータ分離、バックアップと復元試験。
6. API・地図・AIの月次請求責任者とアラート運用。
