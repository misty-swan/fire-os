## 2. Jevの実API契約

Cloudflare経路は`env.AI.run('typesafe/jev', {state, questions})`。stateに最小化本文/必要業務情報、questionsにサーバー固定の質問定義。チャットmessages専用モデルとは異なる。JSON例は架空であり実呼出し未実施。

```json
{
  "state": {"note":"格納箱の前に資材が置かれていた（架空）"},
  "questions": {
    "category": {"type":"choice", "instructions":"報告の代表分類を選ぶ", "criteria":{"equipment_issue":"設備の問題", "access_obstruction":"接近障害", "missing_equipment":"収納物不足", "no_issue":"異常報告なし", "other":"その他"}},
    "needs_check": {"type":"noul", "instructions":"追加確認が必要という記述があるか", "criteria":{"true":"未確認・曖昧・確認依頼", "false":"追加確認の記述なし"}}
  }
}
```

戻り値はmodel/answers/usage。choiceはchoice/probabilities/confidence、noulは0〜1のnoulでbooleanでも別confidence付きでもない。scoreを使う場合は尺度上のscore/legend/probabilities/confidence（小数もあり）。キー/型/数値範囲/許可カテゴリ/応答サイズを検証する。未知型/空出力/timeout/入力上限はmanual_reviewへ。原本を失わず失敗表示する。[Cloudflare Jev](https://developers.cloudflare.com/ai/models/typesafe/jev/)、[TypeSafe API](https://docs.typesafe.ai/api)、[Confidence](https://docs.typesafe.ai/confidence)

カタログのcontextは32,000 tokens、入力$0.042/100万tokens・出力$0、third-party/ZDR Yes。質問/選択肢を含む実token量で計算する。TypeSafe直APIのモデル版/上限/データ保持をCloudflare経路へ転記しない。Jevの日本語品質・版固定可否・無料枠適用はV04で実証。日本語業務表現に英語同等精度があるとは断定しない。[TypeSafe Models](https://docs.typesafe.ai/models)

代表カテゴリと複数補助フラグを分離し、複数異常を単一分類へ隠さない。`needs_manual_review`はアプリ側保留状態で、no_issueやotherと別。confidenceを現実の異常確率/正答保証と表示しない。high confidenceでも承認を省略しない。

## 3. 保存・実行・承認

jobsは原本/版/質問設定と同じD1 commitに保存（02）。workerは現在の送信許可・元版を再検査し、最小化inputのhashと参照版を記録。出力/実モデル版/質問版/usageをai_evaluationsへ保存。失敗の再試行上限、古いlease結果拒否、同一元版＋質問版dedupeを強制。外部推論の再課金完全一回性は保証せず上限/計測で管理する。

レビューには原文、元の版、AI候補、確定予定値、対象タスク/通知、現権限を表示。承認要求はsourceVersion/proposalVersionを含む。元/権限/提案版変化でstale/409、二重決定はeffectOperationId UNIQUEで防止。人の確定分類・理由・reviewedAtは生出力JSONと別保存。通知の実送信はAPI-64の対象/本文承認まで行わない。

## 4. 生成LLM

モデル/JSON対応/コンテキスト/日本語品質/推論単価はD16/V04で固定する。API-32はactivity/result/templateの版から入力を構築し、本人連絡先/Secretを含めない。人数/時刻/集計はサーバー計算。構造出力を検証してdraftText/missingFields/sourceVersionsをreport_versionsへ保存する。JSON適合を事実一致と同一視しない。

未記載の人数/終了時刻/活動/無事故等を補完しない。本文を元実績と比較し、不足項目・引用参照を表示する。入力更新はstaleにし再確認。人編集→新版→承認→配布の順。承認版は不変、訂正は新draft。LLM障害時は手動下書きで業務記録を継続するが、LLM機能そのものの品質未達を正式リリース時に免除しない。独立の計画書/連絡文生成はD01のIDなし候補の扱いを確認する。

## 5. RAG・文書の版とACL（設計案で開発/検証、実運用採用は提案時確認）

1. PER-11管理者が許諾原本をprivate添付として登録しdocument/versionを作成。原文抽出は画像PDF/OCR必要性をD20で決定し、ページ/節/文字offsetを保持する。
2. 承認済有効版だけをchunk化/索引化。索引基盤はD16：D1全文検索＋引用抽出案、またはWorkers AI embedding＋Vectorize案を比較。検索品質が要件に届かなければ再設計し、単なるキーワード結果を根拠ある回答と偽装しない。
3. 検索前にunit/document ACLを絞る。外部索引はunit/version/ACLタグでfilter、topK後の不足も明示し、生成へ渡す前にD1の現ACL/版を再検査。
4. 根拠はdocumentId/version/chunk/page/section/quotedSpan付き。生成した引用を原文位置と突合し、引用がない回答はabstainedとする。根拠不足/矛盾/失効資料では「確認できない」と返す。
5. ACL変更/撤回はD1側で即除外しdeindex jobを作る。索引削除が遅れてもD1再検査で漏らさない。保存回答の再取得と引用原文取得でも現ACLを検査し、失効根拠をマスク/回答失効する。

横断assistantは許可read toolのみ使用し、書込/通知は差分のproposalとして返す。承認は通常業務サービスを通り、AI専用の認可迂回書込を持たない。非信頼本文/文書をsystem instructionに混ぜない、外部URL/ツール名をモデルに自由選択させない。
