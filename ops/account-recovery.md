# アカウント回復の手順（T010、D04）

目的：パスワードや認証アプリを失った利用者を、**本人確認なしに二要素認証が外れたり、他人が入ったりしない**形で復帰させる。

## 1. 回復の手段（利用者側）
| 状況 | 手段 | 備考 |
|---|---|---|
| 認証アプリが使えない | ログイン画面の「回復コードを使う」。コードは各一回限り（使ったコードの再利用は拒否） | 設定時に8個。コードが残り少なければ、ログイン後に「二要素認証・回復コード」で再発行（パスワードの再入力が要る。旧コードは全て無効） |
| パスワードを忘れた | ログイン画面の「パスワードの再設定」。登録の有無は画面に出さない。再設定コードは1時間有効・一回限り。成功すると他端末のログインは全て解除される | **配送手段（メール等）はD04未決で未実装のため、staging/production相当では現状、再設定コードを受け取る手段がない（＝パスワードを忘れた利用者の復旧は未完成）**。D04で配送を決めて実装するまで、検証では試験で捕捉する（下記） |
| 端末を紛失 | 別端末から管理者に連絡 → 管理者がAPI-38で当該利用者の全セッションを失効 | 失効後は、パスワードの再設定または回復コードで入り直す |

## 2. 管理者が使えなくなった場合（紛失時の別管理者手順）
通常のパスワード再設定と回復コードを優先する。両方失った場合だけ、次の二者確認の手順を使う。
1. **別の管理者**が、管理画面で本人確認（対面または既存の連絡網での声かけ）を行い、対象を確認する。1人だけの管理者の場合は、管理主体（分団長等）が立会う。
2. 別の管理者が当該管理者の全セッションを失効（管理画面の「全セッション失効」＝API-38）。
3. 本人は再設定コードで新しいパスワードを設定する（**配送が未実装の間は成立しない**。上の表のとおり）。**二要素認証の解除機能は提供しない**（API・画面とも。回復コードの再発行はログイン後にパスワード再確認で行える）。回復コードも失った場合の復旧は**未確定**：停止した団員は同じメールアドレスで再登録できない（認証側のメールが一意で旧アカウントが残る）ため、暫定として別のメールアドレスで新しい団員として招待し直す。同じメールでの再オンボードはD04の決定後に設計する。
4. 作業は監査に残る（`user.sessions.revoke` / `member.disable` / `invitation.create`）。実施者・立会者・日時を運用記録に残す。
5. 管理者が一人もいなくなった場合（全員が回復不能）は、`ops/bootstrap-admin.md` の再発行は使えない（初期招待は受領済みのため）。**環境を管理するアカウント（Cloudflare側）での復旧手順**（D1の復元・初期管理者の再作成）を使う。実施前に管理主体の承認を得る（docs/07 §7、D17）。

## 3. 配送手段が未決の間の扱い（検証環境）
- 招待tokenと再設定コードは、画面にもAPI応答（再送時）にも再表示されない。発行時にだけ取得できるので、管理者が控えて本人へ安全な経路で渡す。
- 局所環境の試験では、配送コールバック（`AuthDeps.deliverReset`）を差し替えて捕捉する。本番系にはこの経路がなく、何も配送しない。
- D04が確定したら `src/server/auth/config.ts` の `sendResetPassword` にだけ配送を実装する（コードを応答・ログ・監査に出さない）。

## 4. やってはいけないこと
- 本人確認なしでの二要素認証の解除・パスワードの代理設定
- 招待token・再設定コード・回復コードのチャット/メール本文/Gitへの貼り付け
- 管理画面を使わないD1の直接更新による権限付与（監査に残らない）
