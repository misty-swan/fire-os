# 正副管理・管理者不在時の代行・鍵/アカウント復旧の手順（T084）

目的: 管理者が1人しかいない状態（属人化）を避け、**正担当の管理者が不在・端末紛失・回復不能**のときに、副担当が本人確認つきで代行し、業務（団員の追加・招待・権限変更・セッション失効）を止めない。正本は docs/07 §2/§7、docs/14 D17（管理主体・代行。**推奨案＝正副担当＋復旧の二者確認。未承認**）。回復の細部は ops/account-recovery.md、初期管理者は ops/bootstrap-admin.md、鍵の漏洩は ops/security-response.md §4 を正とし、ここでは重複させずに順序と担当だけを定める。

**現状の正直な限界（2026-10-19時点）**: §3の手順は**ローカルのe2e演習で、架空の正担当・副担当（どちらも二要素認証あり）を作って実施**した（`tests/e2e/dependency-outages.spec.ts` scenario 6）。**実在の人による正副の交代演習、別担当（人）による手順の再現は未実施**（提案時TODO。docs/evidence/V07-outage.md「未実施」）。

## 1. 平常時の体制（D17の推奨案を検証設定として使う。未承認）

| 項目 | 推奨（検証設定） | 確認の仕方 |
|---|---|---|
| 管理者の人数 | 正担当1名＋副担当1名以上（役割「管理者」を2名以上に付ける） | 管理画面（`/app/admin`）の「管理する団員」で役割に「管理者」が付いた団員が2名以上 |
| 二要素認証 | 管理者は全員必須（未設定だと管理操作が拒否される） | 各管理者が「二要素認証・回復コード」を設定済み。回復コード8個を各自が紙で保管 |
| 最後の管理者の保護 | 最後の1名は停止・降格できない（画面に「最後の管理者は停止・降格できません」） | 仕組みで保証（tests/e2e/member-admin.spec.ts） |
| 環境管理者（Cloudflare/Google） | 管理者とは別のアカウント。2名以上がログイン手段を持つ | Cloudflareダッシュボードのメンバー（実環境。未実施） |
| 連絡 | 正副担当・分団長の連絡は既存の連絡網（電話等）。アプリの通知に頼らない | ops/contact-flow.md |

## 2. 不在の判断

次のどれかで「正担当不在」とし、副担当が代行を始める。判断と開始時刻を運用記録（紙可）に残す。

1. 正担当本人から端末紛失・入院等の申告があった（既存の連絡網で）。
2. 正担当に連絡がつかず、管理操作（招待・停止・権限変更）が業務上待てない。
3. 正担当のアカウントの不正使用が疑われる（→ ops/security-response.md を先に）。

## 3. 代行の手順（ローカル演習で実施した操作）

前提: 副担当は管理者の役割を持ち、二要素認証を設定済みで、自分の端末でログインしている。

1. **本人確認**（二者確認）: 副担当は、正担当本人または分団長に既存の連絡網で事情を確認する。副担当1名だけで決めない（D17推奨案）。
2. **正担当の全セッションを失効させる**（端末紛失・不在時。アカウント自体は使えるまま）:
   - 管理画面（`/app/admin`）→「管理する団員」から正担当の行を押す → 見出し「<氏名> の管理」を確認。
   - 「利用停止・セッション」の「**全セッションを失効させる**」→ ダイアログ「全セッションの失効」の「理由」に事情（例: 正担当の不在・端末紛失の申告）を入れる →「失効させる」。
   - 「**全端末のログインを解除しました**」が出れば完了（「解除を再試行しています」の場合も、正担当の古いログインはすでに業務の操作ができない）。
   - 効果: 正担当の端末で開いていた画面は、次の操作でログイン画面（`/login`）へ戻る（演習で確認）。
3. **業務を続ける**（副担当だけで可能なことの確認。演習で実施）:
   - 団員の追加: 団員名簿（`/app/members`）→「団員を追加」→ 氏名・役職・班 →「団員を登録」。
   - 招待: 管理画面で団員を選ぶ →「招待先のメールアドレス」→「招待を発行する」→ 表示された「招待リンク」を本人へ安全な経路で渡す（**再表示されない**。チャット/メール本文/Gitに貼らない）。
   - 権限変更・停止も同じ画面（「変更内容を確認する」「停止の内容を確認する」）。いずれも監査に残る。
4. **正担当が戻ったとき**: 正担当は自分のパスワード＋認証アプリ（または回復コード）で再ログインする。代行中の操作は管理画面（`/app/admin`）の「監査ログ」で正担当が確認する（画面の表示名:「全セッションを失効」「団員を登録」「招待を発行」「役割・担当を変更」「団員を停止（休団・退団）」）。
5. **正担当が回復不能のとき**（パスワードと認証アプリと回復コードをすべて失った）: ops/account-recovery.md §2 の二者確認の手順。**二要素認証の解除機能は無い**（意図どおり）。暫定は別のメールアドレスで新しい団員として招待し直し、副担当が管理者の役割を付ける。旧アカウントは「利用停止」（理由を記録）。
6. **管理者が全員回復不能のとき**: `ops/account-recovery.md` §5 のCloudflare側復旧手順（**T086で整備済み。stagingでの演習は未実施**）。アプリ内では復旧できない（初期管理者の再発行 `ops/bootstrap-admin.md` は初期招待が受領済みなら拒否される＝already_bootstrapped/admin_already_linked。`ops/backup-restore.md` の復元は新しい別環境への復元のみ）。それまでの間は、管理者を常に2名以上に保ち（§1）、回復コードを各自が保管することで、この状態を作らない。発生したら分団長へ報告し、環境管理者と対応を決める（実施前に管理主体の承認。docs/07 §7、D17）。

## 4. 鍵・Secretの復旧

| 対象 | 平常時の保管 | 失った/漏れた疑いのとき |
|---|---|---|
| 管理者の回復コード | 各自が紙で保管（8個・各一回限り） | ログイン後「二要素認証・回復コード」で再発行（パスワード再確認。旧コードは全て無効） |
| `BETTER_AUTH_SECRET` | Cloudflare Secrets（`wrangler secret put`。設定ファイルに書かない） | ops/security-response.md §4（rotateしてから調査。全セッションが無効になる＝全員再ログイン） |
| Google Mapsのブラウザキー | 環境別。リファラー/API制限つき（露出前提。docs/07 §6） | キーの発行と**Googleコンソール側の割当・制限の手順は ops/demo-deploy.md §4.3・§5 に整備済み（T086）**。Maps JavaScript APIが未接続（T021/V05）のためキー自体がまだ無く、実環境での発行・設定は接続後に残る。漏洩時の再発行は ops/security-response.md §4（rotateしてから調査） |
| Cloudflareアカウント | 環境管理者2名以上が二要素つきで保持（提案） | **管理者全員回復不能時のCloudflare側（D1・初期管理者）の復旧手順は ops/account-recovery.md §5 に整備済み（T086。stagingでの演習は未実施）**。Cloudflareアカウント自体の回復（外部サービスの手続き）は本リポジトリの範囲外のまま。分団長へ報告 |
