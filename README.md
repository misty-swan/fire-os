## docsの更新方針

**docsは凍結しない。** 実装・技術検証・テストで分かったことに応じて、設計書、API、ER図、画面、受入条件、ロードマップ、実装タスクを随時修正してよい。現在のファイル名・関数名・方式・タスク分割も更新可能で、通常の設計詳細の修正ごとに確認待ちで開発を止めない。

変更時は、関係する設計・実装・テスト・要件対応表を一緒に整合させ、変更理由と影響をGitのコミットに残す。重要な方式・要件の意味・採用範囲の変更は14にも記録し、ユーザーの目的や指示を変える判断が必要な場合だけ確認する。既存IDは追跡に使い、分割・追加・廃止時は対応関係を残す。

12のv0.2原文台帳とREVIEW_REPORTは過去の記録であり、現行設計の変更を禁止するものではない。正式リリース時は判定に使った版・対象・試験結果を記録し、その後もdocsは更新できる。変更で影響する試験・判定は再確認する。固定datasetや承認済み業務記録の不変性は、設計文書の編集可否とは別に扱う。

## プロトタイプと公開

`prototype/` のFireOS Prototype.dc.html（スマホ）、FireOS Desktop.dc.html（PC）、FireOS Design System.dc.html、FireOS Directions.dc.htmlは**画面構成・導線・見た目・文言の正本**で、実装（React）はこれに合わせる。docsはprototypeに合わせて修正し、prototypeが示さない業務規則・権限・状態遷移・API・DBを補う（食い違いはprototypeを優先）。プロトタイプ内の版数は資料自身のもの。prototypeが予告ページ・疑似データ・開発用タグ（PHASE表記等）としている部分は、docs/03「prototypeから意図して変えた点」に記録して実装する。架空データのみを公開し、実名簿/実出動/非公開水利/現場写真をGit/公開画面へ載せない。

## 画面を手元で見る

`npm run demo`（初回は管理者の招待リンクが表示される。一度しか表示されない）→ ブラウザで `http://localhost:8787/login`。前回のデータのまま再起動できる。最初からやり直すときは `npm run demo:reset`。架空データ・ローカルのD1だけで、実Cloudflareにはつながない。止めるときは `Ctrl+C`。デモのログイン情報（メールアドレス・パスワード）は、Git管理外の `.env.demo-login` に控えてある（二要素の6桁は認証アプリ）。保存済みのスクリーンショットは `docs/evidence/ph1/`。
